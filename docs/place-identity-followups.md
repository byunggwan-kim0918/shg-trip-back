# 장소 신원·연결 후속 과제 (전 세계 확대 전 필수)

일본 장소 데이터·검색 개선(2026-11-25 종료)에서 남은 구조 문제다. 일본 실험 DB(trip_jp)에서는 `place-pipeline/bench/sync_core.py`로 맞췄지만, 이 도구는 실험 DB 전용 보정이다. 아래 과제는 일본만의 스크립트로 풀지 않고 **모든 국가·공급처에 같은 구조로 적용**해야 한다. 해결 전에는 다른 국가로 적재 범위를 넓히지 않는다.

## 1. policy 비활성화로 보강 완료 장소가 새 id·보강 없는 행으로 바뀐다

- **현상:** 파이프라인을 다시 돌리면 R3 중복 보류(167건)와 선별 제외(139건)로 core 행 306건이 'policy'로 꺼진다. 그중 302건은 Haiku 보강까지 끝난 행이다.
- **결과:** 같은 장소의 다른 원천 행(대개 Overture)이 카탈로그에서 새 id로, 보강 없이 올라온다.
  - 예: 다카야마 「日枝神社」(id 2793) → 「日枝神社【荒楠神社の場所】」
- **원인:** "원천 행이 풀에서 빠짐"과 "장소가 사라짐"을 구분하지 않는다. 같은 장소를 가리키는 다른 원천 행이 남아 있어도 장소 자체를 끈다.
- **완료 기준:** 원천 행만 바뀐 경우에는 장소 id·보강·임베딩이 그대로 유지된다. 장소가 실제로 없어졌을 때만 비활성으로 바꾼다.

## 2. 대표 원천이 바뀌어도 장소 id와 보강을 유지하는 공통 식별·연결 구조

- **현상:**
  - 중복 묶음의 대표 행이 재실행마다 바뀐다(정보 점수·공급처 우선순위).
  - 대표가 부속 시설·입점 매장이 되는 경우도 있다(「国立文楽劇場 資料展示室」, 「無印良品」↔「アキバ・トリム」).
  - trip_jp에서는 대표가 core 밖이면 기존 행에 대표 FSQ id를 덧다는 방식(132건)으로 버텼다.
- **필요한 구조:** 장소(안정 id)와 원천 행(공급처·원천 id·릴리스)을 분리한다.
  - 장소 1개에 원천 행 여러 개가 붙는다. 대표 변경은 연결 정보만 바꾸고, 장소 id와 파생 데이터(보강·사실·임베딩·이름 별칭)는 유지한다.
  - 원천 행이 가진 다국어 이름은 그 장소의 별칭으로 남긴다. 그래야 대표가 영어 이름 행으로 바뀌어도 현지어 이름 검색이 끊기지 않는다(팜 도미타, 가네모리 사례).
  - 장소를 합치거나 나눌 때는 옛 id → 새 id 이동 기록을 남기고, 일정·대안·표지 참조가 그 기록을 따라간다.
- **완료 기준:** 같은 원천 데이터로 파이프라인을 두 번 돌려도 장소 id가 하나도 바뀌지 않는다. 대표 변경이 보강 재실행을 부르지 않는다.

## 3. PlaceLinkJob이 파이프라인의 SAME 연결을 푼다

- **현상:** `PlaceLinkRepository.replaceLinks`는 지역 단위로 "판정 캐시(`place_pair_verdicts`)에 없는 합침"을 푼다. 그래서 sync_core가 건 SAME 46건은 링크 배치 한 번에 모두 풀린다. 무효화 배치(`PlaceInvalidationJob`)도 지문이 바뀐 행의 합침을 푼다.
- **원인:** 같은 장소 판정이 파이프라인 dedup과 앱 PlaceLinkJob 두 곳에 있다. "한 규칙은 한 곳에서 판정" 원칙에 어긋난다.
- **완료 기준:** 합침의 출처(파이프라인·LLM 판정·사람 검토)를 한 저장소에 기록하고, 모든 배치가 그 기록만 보고 합침을 만들고 푼다.

## 4. Overture 원천 id를 저장하지 않아 적재 순서로 id를 다시 매긴다

- **현상:** `places`에는 `fsq_place_id`만 있고 Overture id가 없다. 그래서 trip_jp core id ↔ 원천 행은 적재 때 쓴 예산 DB의 정렬 순서로 다시 계산한다(`sync_core.states`, 이름 전수 대조로 확인).
- **위험:** 예산 DB를 잃거나 정렬·필터가 바뀌면 기존 id와 원천 행을 다시 이을 수 없다.
- **완료 기준:** 모든 공급처의 원천 id(Overture GERS id, FSQ id, OSM id, Wikidata QID 근거)를 장소와 함께 영구 저장한다. 재적재는 원천 id로 기존 장소를 찾는다. 원천 id가 릴리스 사이에 바뀌는 경우(Overture 병합·분할)를 처리하는 규칙도 함께 둔다.
