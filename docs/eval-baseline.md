# 국내 여러 도시 — 2026-11-14 (`ItineraryRules` v5)

# 날짜별 직접 선택(v2) — 2026-11-15

# 선택은 그대로, 날짜는 코드가 (v2) — 2026-11-15

v2에 LLM 호출을 더하지 않고 지금의 선택 호출 1회를 그대로 쓰는 구성을 쟀다. `SerialPlanner.plan`이 선택 결과에서 요청 의도(highlight·timing)·거점·숙소·예비 장소를 받고, 날짜는 `DayPicker`가 정한다. 선택 단계가 날짜에 놓은 장소는 두 가지로 쓴다.

- `guided`(`Picks.PREFER`): 같은 거리 고리 안에서는 선택 단계가 고른 장소를 먼저 고른다. 거리를 더 쓰면서까지 따르지는 않고, 선택 식당이 묶음·여행 전체 반복이면 같은 고리의 다른 식당을 고른다. 직접 고르지 못한 선택 장소는 예비 목록에 넣어 빈 시간 채우기와 보충이 쓸 수 있게 한다.
- `picker`(`Picks.IGNORE`): 선택 단계가 놓은 장소를 따로 대우하지 않는다.

두 구성 모두 선택 결과의 짝(pairs)·쉬어 가는 곳(rest) 표시도 순서 계산에 쓴다. 보충은 예비 장소를 거리와 상관없이 먼저 쓰므로, 날마다 그날 기준 장소에서 가까운 고리 밖의 예비 장소는 그날 예비 목록에서 뺀다.

고르는 순서는 요청 의도 장소(한 구간 거리 끝까지) → 가까운 고리의 선택 장소 → 가까운 고리의 나머지 → 먼 고리의 선택 장소 → 먼 고리의 나머지다. 기준 장소는 요청 의도 장소, 선택 장소, 유명도 순으로 정한다.

```bash
java -jar app.jar --spring.profiles.active=local,eval --eval.mode=files --eval.pipeline=v2 --eval.selection=guided \
  --eval.files=prod.jsonl,local.jsonl,joined.jsonl,live.jsonl,multi-city.jsonl --eval.out=build/eval-guided
```

읽는 법

- 기록된 선택 반영 비율은 선택 단계가 날짜에 놓은 장소가 날짜와 상관없이 일정에 들어간 비율이다. v1도 24%를 버린다. 선택 단계는 닿는 범위를 모르고 골라서, 어떤 방식으로 놓아도 4분의 1에서 3분의 1은 들어가지 못한다.
- guided는 picker보다 선택 장소를 16%p 더 살리고 점수도 조금 높다. 대신 같은 종류 끼니(21)가 picker(17)보다 많다.
- 채점기는 선택 단계의 취향이 더 나은지 재지 못한다. guided와 picker 가운데 무엇이 사용자에게 나은지는 같은 기록으로 만든 일정을 나란히 읽어서 정한다. 세 구성 모두 같은 선택 호출 결과를 쓰므로 이 비교에는 LLM 비용이 들지 않는다.
- picker 값이 앞 섹션(81.5·조정 필요 20)과 다른 것은 거점·숙소·예비 장소·짝 표시를 선택 결과에서 받게 됐고, 요청 의도 장소를 가까운 고리보다 먼저 고르게 됐기 때문이다.
- 운영에 연결하기 전에 필요한 것: 사용자가 고른 관광지가 날 수보다 많고 서로 멀면 기준 장소가 되지 못한 곳이 빠질 수 있다. 선택 결과의 날짜 수가 맞지 않아 요청 의도만 쓰는 경로에서는 선택 결과의 숙소를 쓰지 않는다.
- 선택 호출(운영 30일, 113건)은 캐시되는 프롬프트 9,296토큰에 입력 3.2천~1만 토큰(3일 중앙값 4.5천), 출력 300~570토큰이고 약 3초가 걸린다. 생성 전체는 18~26초다. v2가 이 호출을 그대로 쓰면 비용과 대기 시간은 v1과 같다.
- 선택 장소를 한 구간 거리 끝까지 먼저 쓰는 순서도 돌려 봤다. 반영 비율은 0.67로 오르지만 거리 위반 일정이 28건으로 v1과 같아져 쓰지 않았다.
